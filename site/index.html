05 - TOPOLOGY

One host today. A fleet on Friday.

Start with process workers on a single machine. Grow to containers or Kubernetes pods when the work demands it - same controller, same flow, same UI.

External workers

VALIDATED

Long-lived nodes on other machines register back to the controller over HTTP. Multi-machine role separation from day one.

{ "mode": "worker", "role": "developer",
  "controllerUrl": "http://ctrl:9527" }

Process

VALIDATED

Same-host workers spawned on demand and torn down when idle. The recommended first setup - no networking homework.

{ "mode": "controller",
  "workerProvisioningType": "process",
  "workerProvisioningMaxPerRole": 10 }

Docker

VALIDATED

Isolated container workers from the published runtime image, with named volumes for persistent workspaces.

{ "workerProvisioningType": "docker",
  "workerProvisioningImage":
  "ghcr.io/topcheer/teamclaw-openclaw" }

Kubernetes

VALIDATED

Worker pods through kubectl, cluster-native. Same registration, same routing - just schedulers instead of shells.

06 - ON KUBERNETES

One helm install. Every team a CR.

The TeamClaw operator runs in your cluster with a built-in management UI. Each team becomes a TeamClaw custom resource - controller, service, workspace and readiness, all reconciled for you.

$ helm install teamclaw-operator \
    oci://ghcr.io/topcheer/charts/teamclaw-operator \
    --create-namespace -n teamclaw \
    --set token.token=$(openssl rand -hex 24)

→ operator up - UI on :30990 - teams from the web form

Charts publish to GHCR on every chart change. The runtime image layers TeamClaw onto the official openclaw base (2026.10.10) - one schema generation, no drift.

Sign in with GitHub. Let the team run the backlog.

Device-flow GitHub OAuth (no client secret shipped), then TeamAuto takes over: it sweeps your issues and PRs on a schedule, reviews with a joint architect / QA / security panel, and ships fixes as pull requests from task-isolated worktrees - never touching your main checkout.

→
SWEEP

On schedule

New issues, PRs and periodic joint full reviews become role-assigned tasks - deduplicated, budget-capped, fully visible in the activity feed.

→
SHIP

As pull requests

Write tasks execute in dedicated git worktrees and deliver via PR with evidence; reviews land as labeled GitHub comments.

Interrupted mid-task? Checkpointed execution resumes where it left off after a restart - same session, same worktree, up to three attempts, then it fails loud instead of looping.

11 - FAQ

Straight answers.

What is TeamClaw?

TeamClaw is an OpenClaw plugin that turns one or more OpenClaw instances into a virtual software company. One controller routes execution-ready work to role-based workers, blocks on real questions instead of guessing, and syncs everything through git.

How does TeamClaw relate to OpenClaw?

TeamClaw runs as a plugin inside OpenClaw (2026.3.24 or newer). By default it gets its own dedicated agent and workspace, so it never shares the host main agent; external worker nodes can also register back to a controller.

How do I install TeamClaw?

On a machine that already runs OpenClaw with a working model, run npx -y @teamclaws/teamclaw install and follow the guided installer to choose the install mode and the model the team should use.

Where does my work live?

On your own machine, in git. Workers sync before they execute and publish after they finish - nothing important lives only in a chat transcript.

Which deployment topologies are supported?

Start with process workers on a single machine, grow to Docker or Kubernetes pods when the work demands it, or attach external worker nodes on other machines that register back to the controller over HTTP. Same controller, same flow, same UI.
