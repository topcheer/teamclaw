01 - THE LOOP

The loop that actually ships

No forty-ticket speculative backlog. The controller creates work that can start now, then keeps the flow moving stage by stage until the outcome lands.

01

Intake

You describe the outcome. The controller asks the sharp questions and writes execution-ready tasks - not a wishlist.

02

Clarify

Missing decision, credential or infra? The task blocks and asks you. It never improvises.

03

Route

Work lands with the right specialist, carrying a role prompt that knows exactly what its job is.

04

Ship

Results publish through git. The controller opens the next stage, and the loop keeps moving.

02 - A LIVE SHIFT

Watch one shift

Every assignment, block and resume is visible - in the controller UI, over WebSocket, and in the message log. No opaque prompt chaining.

  • Clarifications block the task and wait for a human answer - then resume exactly where they stopped.
  • Task states, worker health and idle pools update live in the UI.
  • Full workspace browser: files, diffs and delivery reports, not a wall of chat.

04 - TOPOLOGY

One host today. A fleet on Friday.

Start with process workers on a single machine. Grow to containers or Kubernetes pods when the work demands it - same controller, same flow, same UI.

External workers

VALIDATED

Long-lived nodes on other machines register back to the controller over HTTP. Multi-machine role separation from day one.

{ "mode": "worker", "role": "developer",
  "controllerUrl": "http://ctrl:9527" }

Process

VALIDATED

Same-host workers spawned on demand and torn down when idle. The recommended first setup - no networking homework.

{ "mode": "controller",
  "workerProvisioningType": "process",
  "workerProvisioningMaxPerRole": 10 }

Docker

VALIDATED

Isolated container workers from the published runtime image, with named volumes for persistent workspaces.

{ "workerProvisioningType": "docker",
  "workerProvisioningImage":
  "ghcr.io/topcheer/teamclaw-openclaw" }

Kubernetes

VALIDATED

Worker pods through kubectl, cluster-native. Same registration, same routing - just schedulers instead of shells.

{ "workerProvisioningType": "kubernetes" }
05 - THE HONEST BIT

Blocked beats guessing.

When a role can't safely continue - a missing product decision, a credential, a dependency that doesn't exist yet - TeamClaw raises a clarification and parks the task. You answer, it resumes. Infra work never pretends the infrastructure is already there.

CLARIFICATION · TASK-1042 · FROM QA

Webhook tests need a Stripe key. Which environment - test, or the sandbox mirror?

06 - COLLABORATION

Git is the team's memory.

The controller initializes the repository. Workers sync before they execute and publish after they finish. Nothing important lives only in a chat transcript.

STEP 1

Sync

Workers pull the workspace repo before task execution starts.

→
STEP 2

Execute

Role work happens on its lane, with diffs you can actually review.

→
STEP 3

Publish

Push to the configured remote - or bundle through the controller.

No external Git service? No problem. The controller hosts bundle endpoints so distributed workers keep syncing. Configure a gitRemoteUrl and workers switch to plain clone / pull / push the moment it's reachable.

07 - AUTONOMOUS LOOP

Sign in with GitHub. Let the team run the backlog.

Device-flow GitHub OAuth (no client secret shipped), then TeamAuto takes over: it sweeps your issues and PRs on a schedule, reviews with a joint architect / QA / security panel, and ships fixes as pull requests from task-isolated worktrees - never touching your main checkout.

BIND

One click

Pick a repo; access is verified, clone and repo-convention learning run in the background while you watch staged progress.

→
SWEEP

On schedule

New issues, PRs and periodic joint full reviews become role-assigned tasks - deduplicated, budget-capped, fully visible in the activity feed.

→
SHIP

As pull requests

Write tasks execute in dedicated git worktrees and deliver via PR with evidence; reviews land as labeled GitHub comments.

Interrupted mid-task? Checkpointed execution resumes where it left off after a restart - same session, same worktree, up to three attempts, then it fails loud instead of looping.
